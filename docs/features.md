## 8. 【新增】屏幕时间自动计分

### 8.1 已定设计决策

| 决策项 | 结论 |
|---|---|
| 计分方向 | **双向**：当日总时长 ≤ 阈值 → 加分；> 阈值 → 减分 |
| 迟到数据 | **补算但不回滚**：按原日期补记一条，已发出的分不动 |
| 幂等键 | `screen:<YYYY-MM-DD>:<memberId>`，已存在则直接返回成功、不重复计分 |
| 上报频率 | **每日汇总一次**（受 KV 单键 1 次/秒写入限制倒逼） |
| 采集口径 | Android `UsageStatsManager`，排除系统应用与息屏时段 |
| 认证 | 设备令牌（`x-device` 头），独立于用户账号，可单独吊销 |

### 8.2 语义边界（必须明确，否则实现必然返工）

> **「补算不回滚」的直接后果：某天的判定结果在首次上报时即锁定。**

| 场景 | 结果 |
|---|---|
| 当天 12:00 上报 100 分钟（达标 +2），21:00 实际上涨到 200 分钟 | 已锁定为 +2，**不会再变成 -3** |
| 当天完全没上报，次日补上 150 分钟 | 按 `screen:<昨日>:<member>` 补记 -3，历史不变 |
| 同一份数据重复提交 | 幂等键命中，返回成功但不加分 |
| 阈值被管理员事后修改 | **不追溯**，历史判定保持原样 |

**⚠️ 需确认的细化项**：是否允许「当天内覆盖」（同一自然日内多次上报，以最后一次为准，跨天则锁定）？
这能在不违反「不回滚」的前提下解决上表第一行的失真问题，但会让实现复杂度上升一档。**当前清单按「首次上报即锁定」记录，待定。**

### 8.3 数据模型变更

```
state.devices: [{
  id, name,              // 设备标识与备注名，如「小明的红米」
  memberId,              // 绑定成员，上报只作用于该成员
  tokenHash,             // 设备令牌哈希，明文仅生成时返回一次
  revoked,               // 吊销标记
  createdAt, lastSeenAt
}]

state.screenRules: [{
  id, memberId,          // 每成员一条规则
  thresholdMin,          // 日阈值（分钟）
  bonusPoints,           // 达标加分
  penaltyPoints,         // 超标减分（正数，实际记负分）
  enabled
}]

state.screenReports: [{
  dedupeKey,             // screen:<date>:<memberId>
  memberId, date, totalMin,
  points,                // 本次结算分值（含 0）
  recordId,              // 关联的积分记录 id
  reportedAt
}]
```

> **必须**在 `emptyState()` 中为三个新键补默认值 `[]`，否则老数据读取时为 `undefined`，`.map()` 直接抛错。

### 8.4 后端接口

| # | 接口 | 鉴权 | 状态 | 说明 |
|---|---|---|---|---|
| 8.4.1 | `POST /api/device/report` | `x-device` | ⬜ | body `{ date, totalMin }`；返回 `{ ok, settled, points, reason }` |
| 8.4.2 | `device/add` | admin | ⬜ | 生成令牌，返回明文一次，之后只存哈希 |
| 8.4.3 | `device/list` | admin | ⬜ | 设备列表含 `lastSeenAt` |
| 8.4.4 | `device/revoke` | admin | ⬜ | 吊销令牌，立即失效 |
| 8.4.5 | `screenRule/save` | admin | ⬜ | 按成员 upsert 阈值与分值 |
| 8.4.6 | `screenRule/del` | admin | ⬜ | 删除规则 |

**结算逻辑（伪代码）**：

```
key = `screen:${date}:${memberId}`
if (screenReports.some(r => r.dedupeKey === key)) return { ok:true, settled:false, reason:'已结算' }

rule = screenRules.find(r => r.memberId === memberId && r.enabled)
if (!rule) return { ok:false, error:'该成员未配置屏幕时间规则' }

pts = totalMin <= rule.thresholdMin ? +rule.bonusPoints : -rule.penaltyPoints
if (pts !== 0) {
  member.score += pts
  records.push({ time: 东八区当日12:00, memberId, title: '屏幕时间', points: pts })
}
screenReports.push({ dedupeKey:key, ... })
```

> 复用现有 `score/custom` 的写入形态，但**不能直接调用它**——它是无幂等的，重试会重复加分。

## 10. 平台额度约束（影响设计的硬边界）

| 项目 | 免费额度 | 对设计的约束 |
|---|---|---|
| Workers 请求 | 100,000/天 | 家庭场景无压力 |
| Workers CPU | 10 ms/次 | 现有逻辑 1–3 ms，余量充足 |
| KV 写（不同键） | 1,000/天 | 每次记一笔 = 1 次写；设备上报每日 1 次/成员 |

| KV 读 | 100,000/天 | 充足 |

## 12. 验收要点（新增模块）

1. 同一份上报重复提交 10 次，积分只增加一次。
2. 断网 3 天后恢复，3 天数据全部补记，日期正确，且不重复。
3. 未配置屏幕时间规则的成员上报 → 明确报错，不写入脏数据。
4. 吊销设备后，该令牌立即返回 401。
5. 老数据（无 `devices/screenRules/screenReports` 字段）读取不报错。
6. 设备令牌无法调用任何 admin 接口（越权测试）。
