## 〇之二、积分余额可以为负数（2026-11-06 用户明确）

> **全局不变量**：`members.score` 允许为负、**没有下限**。屏幕时间扣分
> （日总量超标 / 夜间惩罚 / 覆盖重算回滚）扣成负数后**继续扣仍然生效**。
> 这是刻意的「负债」语义，不是并发 bug，**不要给自动扣分补 `score >= 0` 护栏**。

- 反面：**主动支出仍要求余额充足** —— 兑换 / 赠送 / 发布任务冻结三处事务内
  `score < 需要分值` 即拒绝（`ErrInsufficient`），前端按 `affordable` 置灰；
  负余额下这些操作一律不可用。用户原话：「其他的已有分值小于需要的分值无法使用」。
- 每次变动仍写 `records`（8.1 铁律），**负分流水合法**，不因余额为负而截断分值或跳过写入。
- 代码落点：`score INT` 有符号、无 CHECK；`scoring.DayPoints` / `NightPenalty` 返回负；
  `repo/screen.go` 的 `Settle` / `rollbackReport` 只做加减；
  `repo/ledger.go` ×2 + `repo/task.go` ×1 的 `FOR UPDATE` 后余额校验**必须保留**。
- 文档：features 8.4（不变量）、12.1（余额下限）、10.5（澄清只约束主动支出）、
  23 节验收 123–127；行为锁在 `p5_screen_check.sh` 第 10 节。

## 〇之三、账号字段与待确认邀请（2026-11-06 用户明确，P3.1 已实现）

- **`username` 是登录凭证、全局唯一、注册后永不可改**；本来就没有 `UPDATE username` 路径，
  P3.1 把它写成显式不变量：三个改资料接口带 `username` 一律 **400**，不静默忽略。
- **`nickname` 是显示名、可改、1–32 字**，`members` / `admins` **两张账号表都有**。
  早期 `members.name` 语义上本来就是昵称，只是「名称 / 昵称」两套叫法混用；P3.1 统一命名为
  `nickname` + 给 `admins` 补昵称，**不是新造身份体系**。`records.member_name` 是历史流水快照列，保留旧名。
- **组长按用户名邀请必须经对方确认**（`family_invitations` 状态机）；后台 15.2.3 的
  「按用户名直拉入组」是运营方管理动作，语义不同、**保留不动**。两条路径共用同一段 `joinTx` 入组 SQL。
- **未入组可用的接口挂 `/api/app` 组，不能挂 `RequireFamily()` 的 `inFamily`**：
  查收 / 接受 / 拒绝都在 `app` 组；`family_id` 一律取服务端邀请行，
  审计用 `recordAuditAs` 显式传主体（主体此时 family_id 为 NULL）。
- **同组同一人最多一条 pending** 用生成列 `pending_invitee` + `uk_pending_invitee` 下沉到 DB，
  撞 1062 转 409，不做「先查再插」；接受时同事务入组 + 取消其它组 pending。
- **过期惰性判定的隐藏死锁**：`expired` 不主动落库（无定时任务），但生成列只看 `status`，
  一条过期 pending 会永久占住唯一键，而列表又不显示它 → 拿不到 ID 取消、再也邀不动这个人。
  解法：`Create` 同事务先 `UPDATE ... SET status='expired' WHERE expires_at <= now` 再插新行。
  **「不落库」不等于「永远不能落库」，写路径该清扫时必须清扫。**

## 一之三、数据访问层：**维持 sqlx 手写 SQL**（2026-11-05 用户拍板）

> 用户问过「为什么不用 ORM，省得写多套语句」。评估后**决定维持现状**，理由记录在此，
> 避免下次重新争论：
>
> 1. ORM 解决的是「列映射样板」，但会**藏起 SQL**；本项目几条硬约束正好怕这个：
>    多租户 `family_id` 只能从 JWT 取（`Find` 漏 WHERE 即跨组泄漏）、
>    幂等靠条件更新（受影响行数 0 = 已处理，ORM 的 `Save` 表达不了）、
>    覆盖重算要 5–6 步同一事务、`FOR UPDATE` 加锁顺序、不能把 `pass_hash` 带出去。
> 2. 本项目**只有一个数据库**（MySQL），不存在多方言需求 —— sqlx 不是为跨库，是为 SQL 可控。
> 3. 现状规模：repo 层按领域分文件，SQL / 手写列清单 / `FOR UPDATE` 都在同一个目录里，
>    量级现场 `grep` 统计即可（`grep -o 'FOR UPDATE' server/internal/repo/*.go | wc -l`）。
>    换 ORM 等于重写整个 repo 层，风险远大于收益。
>
> ⚠️ **加字段时的规矩（重要，能防静默 bug）**：
> 1. 改 `0001_init.up.sql`
> 2. **先加进 SELECT 列清单**（多列而 struct 缺字段 → sqlx **直接报错**，立刻暴露）
> 3. 再改 `model` 结构体（反过来做，少列会**静默零值**，最难查）
> 4. 再改 `INSERT` / `ON DUPLICATE KEY UPDATE` / `service` 校验 / 文档
> 5. `migrate -verify` + 相关验收脚本
>
> 开发库已存在的表用一次性 `cmd/tmp*/` 工具 `ALTER`，**用完立刻删**（不写增量迁移）。

### v3 强制约定（实现时必须遵守，否则会出安全或数据事故）

9. **多租户隔离是最高优先级**：所有 SQL **必须带 `family_id = ?`**，且 `family_id` **只能从 JWT claims 取**，
   **禁止从请求体、query、路径参数取**。跨组访问返回 **404 而非 403**（避免泄露资源存在性）。
10. **并发写必须走事务**：兑换扣分、屏幕时间结算都要 `SELECT ... FOR UPDATE`，
   否则 MySQL 下会出现负余额（v1 的 KV 单键没有这个问题，迁移后是新风险）。
11. **屏幕时间用「后报覆盖」，不是首次锁定**（19.3 已于 2026-11-02 拍板）：
    `UNIQUE(member_id, report_date)` 保证一天一行，新上报**覆盖**旧值并**重算积分**
    （回滚旧积分 → 删旧记录 → 按新值结算 → `revision+1`）。
    **上报值是「当天累计总时长」，不是增量**——客户端传增量、服务端再累加，会导致重复计分。
    数值未变时直接返回，不要无条件 `revision+1`（设备重试会刷大 revision）。
12. **`/api/state` 不得返回全量 records**：必须服务端分页（v1 是前端分页全量下发）。
13. **记录名快照**：`records.member_name` 冗余存储，避免成员改名污染历史（v1 的缺陷）。
14. **密码一律 bcrypt，不做任何兼容分支**（2026-11-03 随 19.8 更新）：旧数据不迁移 ⇒
    没有旧 SHA-256 哈希存在 ⇒ **不要写惰性改写、不要双算法校验**，注册即 bcrypt、登录只认 bcrypt。
    （原「登录时惰性迁移」的方案已随「一切从 0 开始」作废。）
15. **积分赠送是「转移」不是「计分」**：家庭总积分守恒，不参与连续打卡计数，也不触发违反重置。
    实现必须**按 `members.id` 升序加锁**（否则 A↔B 互赠并发会死锁），余额校验必须在事务内。
    `amount` 恒为正整数，方向由 `from/to` 表达，不接受负数。
    **唯一约束是转出方余额**——不设单笔/每日上限；管理员代赠同样不能凭空生成积分。
16. **任务的经济本质是「转移」，不是「生成」**（2026-11-02 定）：
    发布时从发布者冻结 `score → frozen_score`；审核通过时 `frozen_score -= N` 且完成者 `score += N`，
    **家庭总积分不变**。悬赏分值必须 > 0。
    **任务是公开接取制**：发布后除发布者外任何成员可接取（先到先得，`assignee_id` 锁定），
    **不支持指定完成人**；仅接取者可提交；接取者可放弃（回到 `open`）。
    禁止「发布者接取自己的任务」、禁止「发布者投票」。
    审核幂等靠**条件更新**（`status` 从 `submitted` 改为 `approved`，受影响行数为 0 即已处理）。
    **审核方式为全员投票**（2026-11-02 定）：见第 26 条。
17. **审计日志三条铁律**：① append-only，不提供 UPDATE/DELETE；② **`before/after` JSON 必须剔除
    `pass_hash`**，否则密码哈希进了可查询的表；③ **写入失败不得阻断主流程**（旁路，失败记应用日志即可）。
18. **规则的约束**：`member_ids`（NULL=全组）指定适用范围；`daily_limit` **已随记一笔一并取消**。
19. **屏幕时间只有一条写入路径：设备自动上报**（`source='auto'`；手动上传已移除）。
    `UNIQUE(member_id, report_date)` 保证**同一天只有一条结算记录**，重复上报走**覆盖**：
    「回滚旧积分 → 删旧记录 → 按新值重算」。**不能只改数字，更不能新旧相加**。
    **覆盖导致积分下降是正常行为**，不是 bug。
20. **系统里只有一种规则：睡觉规则**（2026-11-02 定）。
    「记一笔」已移除 ⇒ **不存在手动规则**，`rules.trigger_type` 字段一并删除。
    积分来源只有三种：**任务（转移）、赠送（转移）、睡觉打卡（生成）**；消耗只有**兑换**。
    ⇒ v1 的 `resetStreaksOnViolation` / `namesRelated`、`daily_limit` 全部废弃。
    连续计数按**自然日**，一天最多计 1 次。
21. **「按时睡觉」由屏幕时间自动判定，没有手动入口**：
    只能由 12.4 的夜间判定写入，**没有任何手动入口**。
    **连续奖励档位全部可配置**（用户 2026-11-02 明确）：结构 `[{every, bonus, mode}]`，
    `every`=连续天数阈值、`bonus`=奖励分、`mode`=`repeat`（每满 N 天发一次）/`once`（本轮只发一次）；
    **档位数不限（建议 ≤5）、多档独立计算、同时命中则都发**。改配置**不追溯历史**。
    判定模型是「**可配置的睡觉时间点 + 夜间时段使用时长**」：
    `night_start_hour`（如 0 = 24:00 前放下手机）~ `night_end_hour`（如 7），
    该时段内 `night_min ≤ night_max_min` 即达标，`night_max_min` 建议默认 0。
    **当日未上报视为未达标、连续清零**——防「卸载 App 保连签」的有意取舍。
    **跨零点按开始日归属**：0:00–07:00 的数据记在**前一天**账上，否则当天无法结算。
    一次上报可同时产生日总量与夜间两条记录，`screen_reports` 用 `record_id` 与 `night_record_id`
    分别指向，**覆盖时必须回滚两条**，漏一个就留孤儿记录。
22. **后台是运营者的工具，家庭用户永远没有后台账号**（2026-11-02 用户反复强调）：
    - `admins` = **网站运营者**，**不属于任何家庭组**，**可管理所有家庭组的所有内容**。
      **系统自带默认管理员账号**（部署时由环境变量初始化，首次登录强制改密），
      运营方可在后台新增/停用其他管理员。**不能通过注册页产生**。
    - `members` = 家庭用户（组长/成员），参与积分，**永远没有后台入口**。
    - **创建家庭组只获得前台组长身份，不产生任何后台身份**（这是最容易被误解的一条）。
    登录接口分离：`/api/admin/login` 与 `/api/app/login`；Token 带 `typ` 并校验，互打一律 401。
23. **前台没有管理员，只有组长 `leader`，且每组仅一名**（2026-11-02 定）：
    - **任何成员**：发布/关闭任务、审核任务（不可审自己的）、查看本组全部记录与统计、赠送、自助兑换
    - **组长额外**：增加/踢出成员、配置睡觉时间与奖励规则、管理商城商品
    - **只有管理员**：设备管理、审计日志、家庭组设置、移交管理员
    - **管理员不能发布任务**（不参与积分，无冻结来源）
    首个成员自动为组长；变更组长后旧组长立即失效（不依赖重新登录）。
24. **注册、入组、退出是三件独立的事**（2026-11-02 用户多次纠正后定稿）：
    - **注册 = 用户自己创建账号**，`family_id` 为空，尚不能参与积分。
    - 注册时可顺带**创建家庭组** → 成为组长（**仅前台身份，不产生后台账号**）。
    - **入组有两条路**：① 组长生成**邀请码（有效期 7 天）**，用户输码加入；② 组长按用户名直接邀请。
      **邀请码机制保留，不要废弃**；重置后旧码立即失效。
    - **退出 / 踢出**：`score` 与 `frozen_score` **清零**，`family_id` 置 NULL，
      **写入 `family_bans` 永久禁止再加入该组**（但可加入其他组）；历史记录保留在原组。
    - **不存在「无账号成员」**，也没有「代建账号」。
    Web 不提供成员只读视图（19.1 已关闭）。
25. **配置即租户数据**（2026-11-02 定）：睡觉时间点、连续奖励档位、阈值分值等
    **全部按 `family_id` 隔离并落库**（`rules` / `screen_rules`），
    **禁止写成全局常量、环境变量或配置文件**。不存在「全局默认值」——
    任何默认值也必须落库并归属到具体家庭组。A 组改配置不得影响 B 组。
    层级上 `screen_rules` 是**每成员一条**，所以既支持「组间隔离」也支持「组内按成员差异化」
    （如小学生 21:00、初中生 22:30），后台提供「应用到全组」快捷操作。
26. **任务审核是「全员投票、过半同意」**（2026-11-02 定）：
    有投票权 = **全体成员 − 发布者**；通过条件 = **同意票 > 有投票权人数 ÷ 2**。
    投票期 24h（或任务截止时间取早），超时置 `expired` 且**不转移积分**。
    `task_votes` 表 `UNIQUE(submission_id, voter_id)` 保证一人一票。
    **完成者可以自投**（2026-11-02 明确）；2 人家庭即 1/1 直接通过，**不降级**。
    **仅 1 个有账号成员**时禁止发布任务（无人可投，永远无法过半）。
    **分母 = 家庭组成员数 − 1（发布者）**，所有成员都有账号，不存在例外。
    投票期内成员被踢出，其票作废并**重新计算过半线**。
27. **两个榜单，两种口径**（19.12 已定，2026-11-02）：
    - **积分榜**：按 `score + frozen_score` 降序，回答「我现在还剩多少分」。
      本质是**净额**——兑换、赠送、任务收支**都已结算进余额**，不再单独加减。
      冻结积分**计入**（仍是自己的，只是暂时不能用）。
    - **得分榜**：区间内 `points > 0` 的记录之和，回答「这段时间谁表现好」。
      可切周/月；**不含**兑换消耗、送出赠送、0 分记录；用 `occurred_at` 而非 `added_at` 聚合。
    - 同一成员两榜名次可以不同，这是设计意图，不是 bug。
28. **任务提交只有文字说明、重提 3 次上限**（2026-11-03 定）：**暂不做图片凭证**，
    `task_submissions.image_url` **字段已删除**（不是留着不用）——做图片要额外背上
    上传接口 + 存储目录 + 格式/2MB 校验 + 备份，收益远小于成本；审核本就靠投票。
    同一 `task_id` + `member_id` 的 `rejected` 达 **3 次**即锁定，不能再提；**`expired` 不计入**。
    ⇒ **系统内唯一的文件上传是零**（头像也是预设），不要再假设存在任何上传通道。
29. **头像只做预设，服务器不落任何文件**（2026-11-03 定）：`members.avatar` 存**预设标识**
    （如 `'bear'`，`VARCHAR(64)`），不是 URL；**无上传接口、无图片校验、无头像目录、不进备份**。
    ⇒ 原「本地磁盘 + Nginx / 对象存储」方案作废；日后若放开自定义上传，必须补二次校验 + 备份 + 体积上限。
30. **审计日志保留 180 天、数据库备份保留 30 日**（2026-11-03 定）：日志每日**分批**清理
    （避免长事务），边界按「第 181 天删除」，清理失败不影响主流程；备份滚动期由 7 日**上调到 30 日**
    ——7 日只覆盖「当场发现误删」，30 日才覆盖「月底才发现」。两者口径仍有差距，属有意取舍。
31. **不迁移旧数据，一切从 0 开始**（2026-11-03 定，关闭 19.8）：旧 KV `state` 弃置不用
    （Cloudflare 上原样留着、不删不读），旧账号/旧积分/旧记录**全部不继承**。
    ⇒ **无迁移脚本、无双写窗口、无回滚预案**；任何「兼容 v1 数据」的兜底代码都是多余的。
32. **全服任务与家庭星：已设计、已搁置**（2026-11-03）：完整设计稿存于
    `docs/features.md` **第 25 节**，**不进入当前实现范围**——当前表结构、接口清单、
    验收条目均不含它。将来开工时从 25 节拆回 3/4/11/13/15/19/23 节。
    两条红线必须记住：① 家庭星**不得兑换成个人积分**（否则 8.1 不变量失效）；
    ② 同一任务**每家庭只计一次**（`UNIQUE(global_task_id, family_id)`）。

    一任务一接取）→ 家庭星（独立计价，成立）→ 搁置。

### 6.5 环境与工具坑（长期有效）

- **本机（F 盘机器）mingw64 curl 8.21 把非 ASCII 内联参数按 GBK 发送**：`curl -d '中文'` 入库全是
  U+FFFD，回归大面积假红。跑验收脚本必须
  `export PATH=/tmp/ubin:$PATH`（包装器 exec System32 curl.exe，UTF-8 正确）+
  `PYTHONUTF8=1 PYTHONIOENCODING=utf-8`。详见 2026-11-07 日志。
- **本机 MySQL = phpstudy 8.0.12**，root 密码见 `server/.env` 的 `DB_PASSWORD`（**不写入记忆**，仓库公开）；
  `--skip-grant-tables` 会强制 skip_networking，改密走 `--named-pipe=1` + `mysql --pipe`。

- **回归脚本的管理员密码**：p2 / p8b 会改管理员密码，写死一个值必然集体假红。
  统一走 `scripts/lib_admin.sh` 的 `admin_login()`（先试 `ADMIN_PASSWORD`，再兜底
  `admins1234 / admins123 / admins`）。**新写验收脚本一律 source 它，不要自己拼登录 curl。**
- 本机 `http_proxy` 会吞掉 localhost 请求并返回误导性 502，排查一律加 `curl --noproxy '*'`。
- `p8b_admin_check.sh` 会把默认管理员密码改成 `admins123`，跑完回归需
  `DELETE FROM admins` + `migrate -seed-admin` 复位。
- 数据库是远端开发库；本机起 API 做验收后记得停进程，临时浏览器脚本/截图**验完即删**。
- **DTO 改字段是静默破坏**：`name → nickname` 后 Go 忽略旧字段并回退成 `username`；
  Kotlin `ignoreUnknownKeys = true` + 全默认值字段会把 `{invitation:{...}}` 解析成空对象。
  两端都**不报错**，只有全量回归 + 真实 DOM 点检能发现。改 DTO 必须同轮改所有脚本断言 + 返回体形状。
- **Web 是 hash 路由**：URL 的 pathname 不变，点检判据要用主界面专属元素（如「退出登录」）；
  `page.goto('/#/xxx')` 后要 `waitForSelector` 等目标页元素，固定 sleep 会读到上一页的 DOM。
- 验收脚本内要 `export NO_PROXY=127.0.0.1,localhost`（p12 已内置、旧脚本靠运行时 export），
  否则会话 `HTTP_PROXY` 会把 `127.0.0.1:8080` 变成误导性 502。
- `cmd/devtool` 除 `-points` 外新增 `-expire-invitation <id>`（仅 dev），
  用于走真实的「过期惰性判定」代码，不靠等 7 天，不引 Python MySQL 依赖。
