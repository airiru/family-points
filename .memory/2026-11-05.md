## 续2：屏幕时间每日/每时明细 + 夜间按单位扣分

### 当前进度

Android 屏幕时间页新增「今日每小时」「近 7 天每日」两块明细；后端新增「未按时睡觉按单位阶梯扣分」。
两侧均已编译/接口验证，P5 37/37、P7 25/25 通过。

### 已定结论

1. **小时桶不入库**：服务端只存日总量，`readBuckets` 在设备本地一次 `queryEvents`
   覆盖 7 天、按「天 × 小时」分桶。理由：上传 24 桶×每人×每天无分析价值，上报体涨十倍。
2. **夜间扣分口径**（用户拍板）：超出部分按单位**向上取整**，每单位扣 N 分；
   单位 30/60 二选一，`points=0` 表示不扣（退回旧口径）。
   实现落在 `scoring.NightPenalty`，结算在 `repo.SettleScreen`。
3. **判定权在后端**（用户明确）：「规则全部由后端判断，前端只负责发送和展示值」。
   ⇒ 删掉 Android 页里的本地判定 `nightOK = nightMinutes <= nightMax`，
   改为读服务端 `screen_reports.night_ok`（DTO 补 `night_ok` 字段），未结算显示「待结算」。
4. **`night_rule_id` 由后端推导**：每组只有一条规则（`RuleByFamily`），前端不该知道内部 ID。
   顺手修掉一个潜伏 bug —— App 从来没传过该字段，按旧校验「必填」会一直 400。
5. **改配置不追溯历史**：规则改了不会重算已结算的天；只有重新上报（数值变化）才重算。
   测试时踩到：改完规则再报同样的值，服务端「数值未变直接返回」，看着像没生效。

## 续3：数据访问层维持 sqlx（ORM 议题关闭）

用户问「为什么不用 ORM，省得写多套语句」，评估后**拍板维持现状**。

结论要点（已写进 MEMORY 一之三）：
- ORM 藏 SQL，与本项目几条硬约束冲突：多租户 WHERE 必须显式、幂等靠条件更新、
  覆盖重算多步同事务、FOR UPDATE 顺序、不能带出 pass_hash
- 只有 MySQL 一个库，不存在多方言
- 规模：10 个 repo 文件 / 157 条 SQL / 31 处列清单 / 12 处 FOR UPDATE，换 ORM 等于重写

顺带立了一条防漏规矩：**加字段时先加 SELECT 列、再改 struct**
（SELECT 多列而 struct 缺字段会直接报错；反过来会静默零值，最难查）。
