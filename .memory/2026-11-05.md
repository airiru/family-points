## 续3：数据访问层维持 sqlx（ORM 议题关闭）

用户问「为什么不用 ORM，省得写多套语句」，评估后**拍板维持现状**。

结论要点（已写进 MEMORY 一之三）：
- ORM 藏 SQL，与本项目几条硬约束冲突：多租户 WHERE 必须显式、幂等靠条件更新、
  覆盖重算多步同事务、FOR UPDATE 顺序、不能带出 pass_hash
- 只有 MySQL 一个库，不存在多方言
- 规模：10 个 repo 文件 / 157 条 SQL / 31 处列清单 / 12 处 FOR UPDATE，换 ORM 等于重写

顺带立了一条防漏规矩：**加字段时先加 SELECT 列、再改 struct**
（SELECT 多列而 struct 缺字段会直接报错；反过来会静默零值，最难查）。

## 续5：logout + Web 自动刷新 + 券核销全链路（三项未验全部补齐）

### 当前进度

上一轮记录的「三项未验证」全部做完并验证：logout 接口、Web access 自动刷新、券核销端到端。
后端回归 **282 项全过**（原 270 + 新增 p10 12 项）。

### 已定结论

1. **登出按主体全量吊销 refresh**，不是只吊销本次那一条。
   理由：refresh 是无状态 30 天凭证，「前端丢 token」不等于服务端失效。
   语义定为「该账号所有会话下线」。
   - `POST /api/admin/logout`（需 admin token）
   - `POST /api/app/logout`（需 member token，**不要求已入组**——挂在 `RequireMember` 而非 `inFamily` 组）
2. **登出后旧 access 在到期前仍可用**，这是 JWT 无状态必然的代价，已写进验收 121 条明示。
3. **Web 端 401 先刷新再登出**：`api.js` 加 `doRefresh()` + `refreshing` 共享 promise 做并发去重；
   刷新失败才清 token 跳登录。刷新接口自身 401 不递归。
4. **改密后必须重新登录取新 token**（本轮新发现的坑）：后端改密会吊销全部 refresh，
   而前端原来只调 `loadMe()` 就进后台 —— 当前 access 还能撑 2h，之后再也换不出新 token，
   表现为「用户莫名被踢」。现在改密成功后直接用新密码登录一次，存一对新 token。

   ⇒ 先 `adb shell ime disable com.iflytek.inputmethod/.FlyIME`，输完再 `ime enable` + `ime set` 恢复。
   **必须恢复**，别把用户设备搞坏。
2. **`uiautomator dump` 有时返回上一屏的缓存**，坐标全对不上。
   ⇒ 用 `screencap` 截图 + 按比例换算坐标（截图 1152×2376，看图 540 宽时乘 2.133）。
3. **底部导航节点 bounds 是 (0,0)**（Compose 语义树），dump 拿不到坐标。
   ⇒ 按屏宽五等分估算：x = 1152×(0.1/0.3/0.5/0.7/0.9)，y ≈ 2280。
4. **真机会被人占用**：中途 App 被切到拼多多，点击落到别的应用上。
   ⇒ 动手前先 `dumpsys window | grep mCurrentFocus` 确认前台是本 App。
