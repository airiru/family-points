## 开发阶段铁律确立 + 迁移链 squash 成 1 个

### 用户明确的铁律（已写进 MEMORY 第〇节 / docs 24.6）

> **现在是开发阶段：不兼容任何旧数据、旧代码、旧版本。可以完全推倒重来，数据库可以重新设计。**

推论（改变了既有做法）：
1. 迁移**不做向后兼容**——不写数据迁移、不留旧字段、不要双写窗口
2. `migrate -reset` 是**日常手段**，丢测试数据不算事故
3. 表结构可重新设计，发现设计问题直接改 `0001` 或 squash，**不因「已执行的迁移不能改」而将就**
4. 判据：**任何为了「保住已有数据」而增加的复杂度，当前阶段都是错的**

### 迁移链 squash：5 个 → 1 个

用户问「怎么还有迁移」，随后确认可以推倒重来。原 0001–0005 是历史累积，不是设计需要
（0002 refresh_tokens、0003 redemptions+records.redemption_id、0004 screen_reports.night_ok、
0005 coupons+coupon_votes）。已全部合并进 `0001_init`：

- `records.redemption_id` + `idx_redemption` 直接写在建表语句里（原 0003 的 ALTER）
- `screen_reports.night_ok` 直接写在建表语句里（原 0004 的 ALTER）
- `refresh_tokens` / `redemptions` / `coupons` / `coupon_votes` 四张表追加到 0001 末尾
- `0001_init.down.sql` 补齐四个 DROP

**等真正上线、库里有不可丢的真实数据时，才开始写 0002+ 增量迁移。**

### 教训

**迁移文件数量应该等于「线上库需要演进的次数」，不是「开发过程中改过几次表」。**
