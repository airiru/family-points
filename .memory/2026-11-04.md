### 结论

### 修的 4 个客户端 bug

| # | Bug | 现象 |
|---|---|---|
| 1 | **设备令牌没有任何写入入口**（`TokenStore.deviceToken` 只读） | Worker 拿不到令牌直接 `return success`，**从没上报过**，页面却显示「已与服务器同步」 |
| 2 | `ScreenRuleList` 读 `items`，后端返回 `screen_rules` | 规则永远空列表，夜间配置拿不到；被 `runCatching` 静默吞掉 |
| 3 | `DeviceReportReq.nightMin: Int = 0` | kotlinx `encodeDefaults=false` → **等于默认值的 0 不编码**，服务端当「未判定」，夜间永远不加分 |
| 4 | Worker 用 `firstOrNull()` 取规则 | 多成员家庭会拿别人的夜间配置 |

修法：加令牌配置卡片（保存后 `scheduler.runNow()` 立即补算）；两处 `@SerialName`；
`nightMin` 改 `Int?`；按 `memberIdOnce()` 匹配规则。

### 修的两个服务端 bug

| # | Bug | 现象 |
|---|---|---|
| 5 | `repo.Screen.Reports` 把 `member_id = ?` 直接写进 WHERE | 后台传 `member_id=0` 查全组 → **永远返回空**（成员侧总传真实 id，所以 P5 测试没暴露） |
| 6 | 13 处 `var list []T` | 空结果序列化成 `null` 而不是 `[]`，客户端非空 List 会解析失败 |

### 教训

1. **「显示已同步」这类状态不能靠猜**：原来是「`loadOverview()` 没抛异常 → 认为已同步」，
   结果是永远显示正常。状态要能追溯到**实际前置条件**（有权限 + 有令牌）。
2. **`runCatching` 吞异常会掩盖契约错误**：字段名写错、反序列化失败，全变成「空数据」。
   至少 `.onFailure { Log.w(...) }`。
3. **kotlinx 的 `encodeDefaults=false` 是个坑**：用「0 / false / 空串」当业务值时必须改可空，
   否则这些值在 JSON 里根本不存在。
4. **服务端「可选过滤参数」不要直接写进 WHERE**：`member_id=0` 这种「表示全部」的约定，
   要么在 SQL 层判空，要么在 handler 层拆两条查询。
