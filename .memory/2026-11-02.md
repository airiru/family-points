## 续4：新增积分赠送功能（v3 清单增量）

### 当前进度

在 v3 清单基础上新增「积分赠送」，作为第 10 节插入，原 10–19 节顺延为 11–20。
文档从 470 行增至 636 行。**代码仍零改动。**

### 已定结论

1. **赠送 = 转移，不是计分**：家庭总积分守恒（一方 -N、另一方 +N），
   **不参与连续打卡计数**，也不触发「违反重置」。
2. **记录表达**：一次赠送写两条 `records`（转出 -N / 转入 +N），共享同一 `transfer_id`，
   新增 `source = 'transfer'` 枚举值。这样双方积分流水各自完整，展示层无需特殊拼接。
3. **独立 `transfers` 表**：存转移关系与 `revoked_at`，便于审计与撤销；
   撤销时双方积分回滚、记录标记，而不是物理删除。
4. **加锁顺序**：两行必须按 `members.id` **升序** `FOR UPDATE`，否则 A 赠 B 与 B 赠 A 并发会死锁。
5. **`amount` 恒为正整数**，方向由 `from/to` 表达——不允许传负数，否则语义反转易被误用。
6. **撤销的硬边界**：转出方收到后再花掉，撤销时余额不足 ⇒ **拒绝撤销**，不允许负余额。
   这条必须在实现前想清楚，否则撤销功能会留下脏数据。
7. **命名冲突已处理**：原「转让管理员」接口 `/family/transfer` 与赠送的 `/transfer/*` 混淆，
   已重命名为 `/family/transfer-owner`。

## 续6：新增手动上传手机使用时间

### 当前进度

在屏幕时间章节（第 12 节）下新增 12.4「手动上传手机使用时间」，作为自动采集的兜底通道。
清单 874 → 968 行。**代码仍零改动。**

### 已定结论

1. **定位是兜底，不是替代**。自动采集有四个盲区：未装 App/未授权、iOS、国产 ROM 杀后台、
   换机空档。手动上传覆盖这些场景。
2. **两条写入路径共用同一张表**：`screen_reports` 加 `source ENUM('auto','manual')`、
   `revision`（覆盖次数）、`updated_at`。`UNIQUE(member_id, report_date)` 不变
   ⇒ **同一天只能有一条结算记录**。
3. **冲突规则**（12.4 之三）：
   - 无记录 → 正常结算
   - 已有 `auto` + 管理员 → 允许覆盖
   - 已有 `auto` + 普通成员 → 拒绝
   - 已有 `manual` + 管理员 → 允许覆盖
4. **覆盖必须重算**：回滚旧积分 → 删旧记录 → 按新值结算 → `revision+1`。
   **不能只改数字**（积分对不上），**更不能新旧相加**（会重复计分）。
5. **权限默认仅 admin**。理由：让孩子自己填使用时长等于让他自己定分数，必然少报。
   是否开放成员自助列为 19.17。
6. **重要关联**：手动覆盖策略与 **19.3（自动上报是否允许当天内覆盖）本质是同一件事的两个入口**。
   两者若分开定，会出现「手动能改、自动不能改」的矛盾行为。**必须一起定。**

## 续7：19.3 拍板——屏幕时间改为「后报覆盖」

## 续11：连续奖励档位改为完全可配置

### 当前进度

用户明确「每满 3 天一次这些都可以设置」——连续奖励的天数、分值、是否循环、档位数
都应可在后台配置，不写死。已补全 7.6 的档位模型与 12.5 的示例。清单 1234 → 1277 行。

### 已定结论

1. **档位结构**：`rules.streaks = [{every, bonus, mode}]`
   - `every`：连续天数阈值，整数 ≥ 1，同组内不可重复
   - `bonus`：奖励分，整数 ≠ 0（可为负）
   - `mode`：`repeat`（每满 N 天发一次，3/6/9…）/ `once`（本轮连续内只发一次），默认 `repeat`

3. **`repeat` 与 `once` 的本质区别**：前者按倍数循环，后者只在达到阈值那一次发，

4. **改配置不追溯**：修改 `every`/`bonus`/`mode` 后，历史已结算日期不重算。
5. **保存时校验**：`every ≥ 1`、`bonus ≠ 0`、`every` 不重复、档位数上限——

## 续13：权限重划 + 任务改为悬赏转移

### 当前进度

### 已定结论（本次最重要的一次结构性调整）

**A. 权限重划**
1. **任何成员**：发布/关闭任务、审核任务（**不可审自己的**）、查看本组全部记录与统计、赠送、自助兑换。
2. **组长额外**（**每组仅一名**）：增加/踢出成员、配置睡觉时间与奖励规则、管理商城商品。
3. **只有管理员**：设备管理、审计日志、家庭组设置、移交管理员。
4. **管理员不能发布任务**——不参与积分，没有可冻结的余额。

**B. 移除三项功能**
5. **记一笔**（含自定义事项）——积分必须「有来源」，凭空加分无法追溯。
6. **手动补录使用时长**——与自动上报冲突，且是绕过规则的加分后门。
7. **删除记录**——不可逆，破坏流水完整性。
   ⇒ 接口层直接删除返回 404，**不是隐藏按钮**；验收 35–38 专门测这点。

**C. 任务改为「悬赏转移」**
8. 发布任务时**冻结**发布者积分（`score → frozen_score`），审核通过后转给完成者。
   **家庭总积分不变**。
9. 需要 `members.frozen_score` 字段；`tasks` 表加 `publisher_id` / `escrow_points` / `completed_by`。
10. **禁止发布者 = 完成者**（否则可自己给自己悬赏并自审通过，等于凭空加分）。
11. **禁止审核自己提交的任务**。
12. **悬赏分值必须 > 0**——任务只做转移，不做惩罚。

**D. 积分体系收敛为四种变动**
13. 来源三种：任务（转移）、赠送（转移）、睡觉打卡（生成）；消耗一种：兑换（销毁）。
14. 不变量：`家庭总积分 = Σ睡觉奖励 − Σ兑换消耗`，**转移不改变总量**。这是验收核心口径。
