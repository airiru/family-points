## 续1：屏幕时间功能选型与全项目功能清单

### 当前进度

用户提出「QQ/微信能否获取手机使用时间」→ 确认不可行（系统级权限模型限制）→ 选定
「Android 自建 App 上报」方向 → 完成技术选型 → 产出全项目功能清单 `docs/features.md`。
**代码尚未改动**，仅新增文档。

### 已定结论

1. **微信/QQ 无法获取全机使用时长**。成长守护平台只覆盖腾讯系游戏与视频号时长；
   全机时长属系统级数据，Android 需 `PACKAGE_USAGE_STATS`（用户手动授权），
   iOS 的 Family Controls 需 Apple 特批 entitlement，社交类 App 无路径。
2. **Android 端选型**：Kotlin 原生 + `UsageStatsManager` + WorkManager 懒上报 + 侧载分发。
   排除 Flutter/RN（为单一功能引入重运行时，且 iOS 端本就不可行）。
3. **认证方案**：新增设备令牌（`x-device`），不复用管理员账号密码——避免密码落在孩子手机、
   且可单独吊销。
4. **计分语义（用户拍板）**：双向——达标加分、超标减分。
5. **迟到数据（用户拍板）**：补算但不回滚。
6. **该决策的直接后果已写入清单 8.2**：某天判定结果在首次上报时即锁定，
   当天后续上涨不会改写结果。已在清单中列为待确认细化项（是否允许「当天内覆盖」）。
7. **平台额度确认**：Workers 免费 100k 请求/天、10ms CPU；KV 免费 1k 写/天、
   **单键 1 次/秒**。后者是「必须每日汇总上报、不能实时推送」这一设计的根因。
8. **语言选型结论**：Workers 语言支持不随套餐变化（JS/TS/Python/Rust/Wasm 均免费可用）；
   真正差别是 CPU 预算。Pages 与 Workers 同为 workerd 运行时，为「换语言」而迁移收益极低。

## 续2：v2 架构决策（D1 + 多租户 + Kotlin 原生全量重写）

### 当前进度

用户下达三项架构级变更：数据库改 D1、后端保持 JavaScript、Android App 用 Kotlin 原生
**包含现有前端全部功能**，并新增家庭组与屏幕时间上报。
已将 `docs/features.md` 重写为 v2（280 → 约 420 行），**代码零改动**。

### 已定结论

1. **存储 KV → D1**。理由：KV 单键写入 1 次/秒是「屏幕时间必须每日汇总」的根因，D1 解除此约束，
   且可取消 500 条记录截断。代价是数据访问层全部重写 + 一次性迁移脚本。
2. **后端保持 JavaScript**。接口协议 `{ ok, state }` 尽量保持不变，使前端改动最小化。
3. **Android 用 Kotlin 原生全量重写**（用户明确选择，非 WebView 套壳）。
   ⇒ 需在 Compose 中重写 17 个界面，是本次工作量最大的部分。**已如实告知代价，用户仍选此项。**
4. **家庭组 = 多租户**：多用户，**每用户只能加入一个家庭组**。
   实现手段：`members.username` 全局唯一 ⇒ 天然保证「一人只属一组」，无需额外关系表。
5. **D1 免费额度关键约束**（已写入清单第 16 节）：
   - rows read 5,000,000/天 → **`/api/state` 不得返回全量 records**，必须服务端分页
   - **queries/invocation 仅 50**（免费）→ 写操作用 `db.batch()`
   - 单库 500 MB、数据库 10 个、单库单线程
6. **多租户硬规则**：所有 SQL 必须带 `family_id = ?`，且只能从 token 取，**禁止从请求体取**。
   这是最容易出跨家庭越权的地方，已列为 v2 强制约定。
7. **记录名快照**：`records.member_name` 冗余存储，修复 v1 中「改名污染历史」的缺陷。
8. **幂等下沉到数据库**：`UNIQUE(member_id, date)`，不只靠应用层查重。
